# 多人版部署上线指南

本文串联「后端（Supabase）」与「前端（PWA）」的部署步骤。后端细节见 `supabase/README.md`。

## 登录方式

**手机号 + 密码**：注册填手机号+密码，登录用手机号+密码。0 成本、无短信资质要求（Supabase Auth 托管密码存储）。

## 〇、环境分工（测试库 / 生产库）

本项目建议建**两个 Supabase 项目**（免费层每个账号/组织可有 2 个活跃项目），互不干扰：

| 环境 | Supabase 项目 | 前端配置文件 | 用途 |
|---|---|---|---|
| 测试 | `<项目名>-test` | `.env` | 本地 `npm run dev` 调试、随便造数据、随便删 |
| 生产 | `<项目名>` | `.env.production` | 真实家人使用，`npm run build` 的产物连它 |

两个后端项目按下面「一、后端部署」各自走一遍；前端配置文件都已被 `.gitignore` 忽略，不会提交。

> 只想要一个环境也行：只配 `.env`，开发与构建都连同一个库。

## 一、后端部署（每个环境各做一遍）

### 1. 创建 Supabase 项目
1. https://supabase.com → 登录 → **New project**
2. Name 如 `dialysis`（生产）/ `dialysis-test`（测试）、数据库密码记好、Region 建议选 `Northeast Asia (Tokyo)` 或 `Southeast Asia (Singapore)`
3. 等 1~2 分钟初始化完成

### 2. 建表 + 权限
- **SQL Editor** → 粘贴 `supabase/schema.sql` 全部内容 → Run
- 脚本**可重复执行**：重复跑不会报错、不会清数据，只会补上缺的列/表/权限策略
- 之前跑过旧版本 schema 的，务必**再跑一次**：新版给 `sessions` 加了医生脱水量与中止信息字段，新增了 `blood_flows` 表，并把 `operator_id` 外键改到 `public.users`（否则查询记录人姓名会报关系错误）
- 同时修正了 `users_select` 策略的列名歧义（`patient_members` 也有 `id` 列，必须显式写 `users.id`）

建出来的表：`users` / `patients` / `dry_weights` / `sessions` / `blood_pressures` / `blood_glucoses` / `blood_flows` / `adverse_reactions` / `patient_members`

### 3. 部署 Edge Functions
```bash
# 安装 CLI（或用 npx supabase@latest 代替 supabase）
npm install -g supabase
supabase login                                   # 或用环境变量 SUPABASE_ACCESS_TOKEN
# 无需 supabase link，直接用 --project-ref 指定

# register 必须免 JWT 校验（注册时还没登录）
supabase functions deploy register      --project-ref <ref> --no-verify-jwt --use-api
supabase functions deploy create-patient --project-ref <ref> --use-api
supabase functions deploy invite-member  --project-ref <ref> --use-api
```
- `--use-api`：不依赖 Docker，直接由平台构建
- 另外两个函数保持默认的 JWT 校验（前端会带用户 access token 调用）
- Windows 也可跑 `supabase/deploy-functions.ps1` 交互式执行

### 4. 获取前端连接信息
**Project Settings → API**：记下 **Project URL** 与 **anon public key**（legacy 的 anon key 兼容性最好）。

## 二、前端部署

### 1. 配置环境变量
```bash
cp .env.example .env              # 填「测试库」的 URL 与 anon key（npm run dev 用）
cp .env.example .env.production   # 填「生产库」的 URL 与 anon key（npm run build 用）
```

### 2. 本地调试
```bash
npm install
npm run dev       # http://localhost:5173，连 .env 里的测试库
```

### 3. 构建生产产物
```bash
npm run build     # 产物在 dist/，已注入 .env.production 里的生产库配置
```

### 4. 部署到免费静态托管
把 `dist/` 上传到：Cloudflare Pages / Vercel / Netlify（免费，HTTPS 必须）。
若托管平台支持环境变量，也可以在那里配 `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` 并在构建时注入。

### 5. APK（可选）
按 `README.md` 的 Capacitor 流程重打包；`@capacitor/preferences` 负责 APK 内持久登录。

## 三、上线验证

1. 手机打开前端 → 登录页 → **注册**（手机号 + 密码）→ 自动登录
2. 「设置 → 账号 → 我的姓名」填上称呼（记录人会显示这个名字，不填则显示手机号）
3. 「设置 → 我的病人」→ 「＋ 新建」建病人（登录后会自动选中上次使用的病人）
4. 「设置 → 上传本地数据到云端」迁移本地数据（可选，含血流量）
5. 「成员管理」→ 邀请家属手机号（对方需先注册登录一次）→ 设置角色
6. 多端登录：家属手机上也能看到该病人，共同记录、查看报告
7. 记录一条完整数据，确认「医生设定脱水量 / 血流量 / 中止状态」在云端也能正常保存与展示
8. 权限抽查：把某个成员改成「医生/只读」后，对方应无法新增记录（数据库会拒绝写入）

## 四、成本

- Supabase 免费层：500MB 数据库 / 5 万月活，家庭/小团队完全够用。

## 五、已知运维要点

- **`sessions.operator_id` 外键必须指向 `public.users`**（不是 `auth.users`）：记录人姓名靠它关联，指向 auth schema 时 PostgREST 关联不出姓名。
- **Edge Function 里识别调用者必须显式传 token**：`supabase.auth.getUser(token)`，service 客户端自身没有 session，用无参 `getUser()` 会永远返回「未登录」。
- **前端调 Edge Function 要带用户 access token**（`Authorization: Bearer <access_token>`）并同时带 `apikey` 头；只有注册接口可以用 anon key。
- `schema.sql` 可重复执行；策略采用「先 drop 再 create」，改动策略后重跑即可生效。
