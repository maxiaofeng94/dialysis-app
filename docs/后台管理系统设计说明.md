## 一、目标与范围

### 要做的

1. **查看注册用户**：手机号、姓名、注册时间、最后登录、账号状态、名下病人数
2. **管理用户与病人的配置**：病人基础参数、成员（角色 / 增删）、账号状态（禁用 / 重置密码）
3. 一切管理动作**留痕可查**（审计日志）

### 明确不做的（一期）

- 不做面向患者/家属的新功能，**不动现有 App 的任何界面与行为**
- 不做数据报表 / 统计大屏（只做基础计数）
- 不做手机号短信、不做微信登录
- 默认**不把临床病历暴露给后台**（见 §7 隐私边界，可调整）

### 硬性约束（来自现状）

| 约束 | 说明 |
|---|---|
| 前端是纯静态 SPA | 只持有 anon key，**安全边界完全靠数据库 RLS 与 Edge Function** |
| service_role 绝不下发前端 | 所有需要 service_role 的操作只能在 Edge Function 内执行 |
| 现有登录是手机号 + 伪邮箱 | `{手机号}@phone.local`（`src/stores/auth.ts:38`），注册走 `register` 函数 |
| 现有 RLS 全量隔离 | 普通用户只能看到「自己是成员」的病人（`supabase/schema.sql:176-308`） |
| 管理员目前不存在 | 没有任何「超级用户」概念，管理员今天连别人的用户列表都看不到 |

## 二、形态选型

### 方案 A（推荐）：同仓库 + 独立前端入口 + 独立 Pages 项目

```
dialysis-app/
├─ index.html            # 现有 App（患者/家属用）
├─ admin/                # 新增：后台入口目录（dev 中间件把 / 指向它的 index.html）
│  └─ index.html         # 后台页面的真实入口
├─ src/                  # 现有代码（不动）
├─ src/admin/            # 新增：后台全部代码
├─ vite.config.ts        # 现有构建（默认只构建 index.html，不含 admin）
└─ vite.admin.config.ts  # 新增：后台构建 → dist-admin/
```

- App 构建产物 `dist/` → Pages 项目 `dialysis`（现状不变）
- 后台构建产物 `dist-admin/` → **新** Pages 项目 `dialysis-admin` → https://dialysis-admin.pages.dev
- 后台代码**不会打进 APK**（`capacitor.config.json` 的 `webDir` 仍是 `dist`）
- 复用同一个 GitHub 仓库、同一套 secrets（`VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`）

**优点**：不进 APK、不增大 App 包、后台可用桌面级组件库、CI 一条命令自动建项目并部署
**代价**：多一个 Pages 项目、多一个 workflow

### 备选

| 方案 | 说明 | 评价 |
|---|---|---|
| B. 并入现有项目 | 产物合成一份 `dist/`，访问 `/admin.html` | 配置最少，但后台代码会随 `cap sync` 进 APK |
| C. 独立仓库 | 彻底隔离 | 两套 npm/CI/依赖升级，家庭项目维护成本过高 |

> ✅ **已确认**：采用 **方案 A** —— 独立入口 `admin/index.html` + `src/admin/**`，构建产物 `dist-admin/index.html`，部署到独立 Pages 项目 `dialysis-admin`，不进 APK。

## 三、管理员身份模型

### 复用现有账号体系（不新建账号）

管理员就是**普通注册用户中的一个**，用**同一个手机号 + 密码**登录后台。登录成功后调一次接口判断是不是管理员；不是就立刻登出并提示「无后台权限」。

理由：零新增账号体系、零短信/SMTP 成本、Supabase Auth 免费层直接可用。

### 权限数据：独立表 `public.admins`（**不**用 `users.is_admin`）

```sql
create table if not exists public.admins (
  user_id    uuid primary key references public.users(id) on delete cascade,
  note       text,
  created_by uuid references public.users(id) on delete set null,
  created_at timestamptz not null default now()
);
```

**为什么不能把 `is_admin` 加在 `public.users` 上**：现有策略 `users_update`（[schema.sql:308](../supabase/schema.sql)）允许用户更新自己那一行，任何人都能把 `is_admin` 改成 `true` 自我提权。独立表 + 不给任何写策略，从数据库层杜绝。

### 判定函数

```sql
create or replace function public.is_admin()
returns boolean language sql stable security definer set search_path = public
as $$ select exists (select 1 from public.admins where user_id = auth.uid()); $$;
```

### 表的可见性

```sql
alter table public.admins enable row level security;
drop policy if exists admins_select on public.admins;
create policy admins_select on public.admins for select using (user_id = auth.uid());
-- 故意不建 insert / update / delete 策略：
-- 普通请求（含管理员本人的 anon key 请求）都写不了，只有 SQL Editor 与 service_role 能写
```

### 首个管理员怎么产生

后台**不提供**自助提权入口。第一次由人工在 Supabase SQL Editor 执行一次：

```sql
insert into public.admins(user_id, note)
select id, '初始管理员' from public.users where phone = '你的手机号'
on conflict (user_id) do nothing;
```

后续管理员可以由现有管理员在后台里授予/撤销（走 Edge Function，且禁止撤销最后一个管理员）。

## 四、数据库变更（增量、幂等）

新增到 [supabase/schema.sql](../supabase/schema.sql) 末尾（保持「可重复执行」风格）：

1. `public.admins` 表 + RLS（见上）
2. `public.is_admin()` 函数
3. 审计日志表：

```sql
create table if not exists public.admin_audit_logs (
  id         bigint generated always as identity primary key,
  admin_id   uuid references public.users(id) on delete set null,
  action     text not null,                      -- 如 user.ban / patient.update
  target_type text,                              -- user / patient / member
  target_id  text,
  detail     jsonb not null default '{}'::jsonb, -- 变更前后摘要（不含密码）
  created_at timestamptz not null default now()
);
create index if not exists idx_admin_logs_created on public.admin_audit_logs(created_at desc);
create index if not exists idx_admin_logs_admin   on public.admin_audit_logs(admin_id);

alter table public.admin_audit_logs enable row level security;
drop policy if exists audit_select on public.admin_audit_logs;
create policy audit_select on public.admin_audit_logs for select using (public.is_admin());
-- 写入同样只允许 service_role（Edge Function）
```

**关键点：现有业务表（patients / sessions / patient_members / 各类测量表）的 RLS 策略一律不动。** 管理员的读写全部经 Edge Function 的 service_role 完成，普通用户视角与今天完全一致，零回归风险。

### 可选加固（建议一并做，属于顺带修复的既有隐患）

现在用户可以更新自己 `public.users` 行的任意列（包括 `phone`）。建议列级收紧：

```sql
revoke update on public.users from authenticated;
grant update (name) on public.users to authenticated;   -- App 只用到改姓名
```

> ✅ **已确认**：做这条加固（App 里只有「改我的姓名」会写 `users` 表，不受影响）。

## 五、后端接口设计：单个 Edge Function `admin-api`

沿用现有函数风格（`create-patient` / `invite-member`，见 `supabase/functions/`）：**service_role 客户端 + `getUser(token)` 显式校验**。

**为什么收成一个函数**：权限校验只有一处，最容易审计；不存在「某个接口忘了判管理员」的风险；CORS、错误格式、审计写入全部复用。

```
POST /functions/v1/admin-api       （保持默认 verify_jwt = true）
Headers: Authorization: Bearer <管理员 access_token>, apikey: <anon key>
Body:    { "action": "user.list", "payload": { ... } }
```

调用链（每个请求都走全流程）：

```
verify_jwt → getUser(token) → 查 public.admins 是否含该 uid
  ├─ 否 → 403 { error: '无后台权限' }
  └─ 是 → action 白名单分发 → 参数校验 → 执行（service_role）
            └─ 写操作：先写审计日志，再执行，返回结果
```

### 接口清单

| action | 说明 | 分期 |
|---|---|---|
| `whoami` | 返回当前用户是否管理员、姓名、手机号 | P1 |
| `stats.overview` | 用户数 / 病人数 / 记录总数 / 近 7 天新增 / 异常项计数 | P1 |
| `user.list` | 分页 + 搜索（手机号、姓名）+ 排序（注册时间、最后登录） | P1 |
| `user.get` | 用户详情：资料、名下病人与角色、每病人记录数与最近记录时间、是否管理员、账号状态 | P1 |
| `patient.list` | 分页 + 搜索；含成员数、记录数、最近记录时间 | P1 |
| `patient.get` | 病人配置 + 成员列表 + 干体重历史（取决于待确认 3）+ 记录聚合 | P1 |
| `member.add` | 按手机号把用户加入病人（不要求调用者是 owner） | P1 |
| `member.setRole` | 改成员角色 | P1 |
| `member.remove` | 移除成员（保护：病人至少保留 1 个 owner） | P1 |
| `user.setBanned` | 禁用 / 解禁（`auth.admin.updateUserById` + `ban_duration`） | P1 |
| `user.resetPassword` | 重置密码（返回一次性随机密码） | P1 |
| `user.rename` | 修改用户姓名 | P1 |
| `patient.update` | 改病人基础配置（姓名 / 生日 / 轮椅重量 / 回水量） | P1 |
| `admin.grant` / `admin.revoke` | 授予/撤销管理员（禁止撤销最后一个） | P1 |
| `audit.list` | 审计日志分页查询（也可走 RLS 直读） | P1 |
| `user.create` | 代建账号（帮不会注册的老人） | P2 |
| `patient.transferOwner` | 转移创建者（创建者失联时救急） | P2 |
| `patient.delete` | 删除病人及其全部数据（要求输入病人姓名确认） | P2 |
| `user.delete` | 删除用户（需选择：仅移除成员关系 / 连同其病人一并删除） | P2 |

### 用户列表的数据来源

`public.users` 只有 `id / name / phone / created_at`，**没有最后登录时间、禁用状态**——这些在 `auth.users` 里，而 PostgREST 不暴露 `auth` schema（service_role 也不行）。因此：

- 用户身份与状态：Edge Function 内用 `supabase.auth.admin.listUsers({ page, perPage: 1000 })` 取
- 业务资料与病人数：service_role 查 `public.users` / `patient_members` 后在函数内合并
- 用户量 < 1000 时一次取完，超过则按页循环取所需页（家庭应用量级下不会有问题）

### 交互与安全细节

- 登录后调 `whoami`；不是管理员 → `signOut()` + 提示，**绝不进主界面**
- 前端**不做权限判定兜底**，所有按钮只影响可见性，真正的拒绝在数据库/函数层
- 危险操作二次确认：禁用账号、重置密码、移除成员、撤销管理员 → 弹窗说明影响并要求点确认（删除类操作要求**手输对象姓名/手机号**）
- 会话：JWT 默认 1 小时过期；前端再叠加**空闲 30 分钟自动登出**
- 重置密码：函数生成一次性随机密码返回，界面提供「复制」，并提示管理员线下告知本人

## 七、隐私边界（重要，需你拍板）

管理员能拿到的是「账号 + 成员 + 病人基础配置」，是否包含**临床数据**，直接决定合规与信任风险：

| 类别 | 内容 | 建议 |
|---|---|---|
| 账号 | 手机号、姓名、注册/登录时间、禁用状态 | ✅ 可见（管理必需） |
| 关系 | 病人 ↔ 成员、角色 | ✅ 可见（管理必需） |
| 病人基础配置 | 姓名、生日、轮椅重量、回水量 | ✅ 可见可改 |
| 聚合数字 | 记录条数、最近记录时间 | ✅ 可见（排障用，不含内容） |
| 干体重 | 干体重历史值 | ⚠️ 倾向不开放（属临床参数） |
| 临床明细 | 透析记录、血压、血糖、血流量、不良反应、备注 | ❌ 默认不开放 |

「不开放」是**数据库层的实现**：不去动 `sessions` / `blood_pressures` 等表的 RLS，因此即使有人伪造请求（甚至拿着管理员 token 直连 PostgREST），也读不到任何病历。

> ✅ **已确认**：选 **A 严格最小** —— 后台只显示记录条数与首末记录日期；干体重与全部临床明细都不开放。

### ⚠️ 这条边界的真实含义（2026-10-02 安全审查补充）

上面说的是"**后台没有病历查询入口**"，不等于"**管理员看不到病历**"。缺口在后台自己的一个功能上：

- `user.resetPassword`（用户详情页「重置密码」）可以对**任意非自己**的账号重置密码，并把新密码明文返回给管理员；
- 管理员拿这个密码在 App 里登录，就能以该用户身份看到其 RLS 范围内的**全部病历**；
- 这一串动作在审计里只留下一条 `user.resetPassword`，**不会**留下"看过哪些病历"的痕迹（读操作本来就不经 Edge Function）。

**结论：管理员在本系统里是超级权限角色。** 因此配套要求是：

| 要求 | 说明 |
|---|---|
| 管理员只能是完全可信的人 | 别为了"方便排查"随手授予 |
| 后台入口收口 | 用 Cloudflare Access（Zero Trust）限制可访问的邮箱/IP，别把 `dialysis-admin.pages.dev` 直接暴露给全网 |
| 管理员账号启用 MFA | Supabase Auth 支持 TOTP；管理员与普通用户共用同一套"手机号 + 密码"体系，密码一弱就全盘皆输 |
| 需要审计级别更高时 | 移除后台的重置密码能力（本项目没有短信/邮件找回通道，代价是用户忘记密码后没有恢复手段），或改为"重置后强制对方首次登录改密" |

**如果哪天要让管理员也读不到病历**，只有两条路：① 去掉重置密码；② 端到端加密（病历内容在客户端加密，密钥只掌握在病人/家属手里）——当前架构不具备。

## 八、部署与运维

### 构建

```jsonc
// package.json 新增
"dev:admin":   "vite --config vite.admin.config.ts",
"build:admin": "vue-tsc -b && vite build --config vite.admin.config.ts"
```

`vite.admin.config.ts` 要点：Vite root 保持**项目根**；dev 用 `configureServer` 中间件把 `/` 重写到 `/admin/index.html`；构建用 `rollupOptions.input` 指定 `admin/index.html`，再用 `closeBundle` 把 `dist-admin/admin/index.html` 提升为 `dist-admin/index.html`。
**不要把 root 设成 `admin/`**：那样 `admin/index.html` 里的入口脚本会解析不到（浏览器按 URL 基准解析成 `/src/admin/main.ts`，而 root 下没有这个文件），表现为「首页 200 但页面白屏」，偏偏构建产物又是正常的，很难察觉。改完这里务必跑 `npm run check:admin-dev`。

`.gitignore` 补 `dist-admin`。

### CI

新增 `.github/workflows/deploy-admin.yml`（与 `deploy.yml` 平行，互不干扰）：

1. `npm ci` → `npm run build:admin`（注入 `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`，复用现有 secrets）
2. `npx wrangler pages project create dialysis-admin --production-branch=main`（已存在时忽略报错）
3. `npx wrangler pages deploy dist-admin --project-name=dialysis-admin --branch=main`

后台更新**不影响** App 的部署链路；App 更新也不触发后台重新部署（workflow 用 `paths` 过滤）。

## 九、安全自查清单（开发完成后逐条实测）

1. 未登录调 `admin-api` → **401**
2. 普通用户（非管理员）token 调 `admin-api` → **403**（逐个 action 抽查，尤其写操作）
3. 普通用户直连 PostgREST 查 `users` / `patients` → 仍只看到自己 + 同病人成员（**验证现有 RLS 未被破坏**）
4. 管理员直连 PostgREST 查 `sessions` → **读不到**（隐私边界在数据库层成立）
5. 普通用户尝试 `insert`/`update` `public.admins` → **被拒**（无法自我提权）
6. 撤销最后一个管理员 → **被拒绝**
7. 每个写操作执行后，`admin_audit_logs` 里都有对应记录（含操作人、对象、时间）
8. 线上后台产物 grep 项目 ref，确认连的是**生产库**；主 App 产物里**不含** admin 代码
9. 禁用某账号后，该用户**重新登录/刷新 token 失败**（注意：已签发的 access token 在过期前仍有效，最长 1 小时）

## 十二、实现落地说明（代码已完成部分）

### 数据库（`supabase/schema.sql` 第 9～13 节，幂等）

| 对象 | 作用 |
|---|---|
| `public.admins` | 管理员名单；**只读自己那一行**，无写策略（只能 SQL Editor / service_role 写） |
| `public.is_admin()` | security definer 判定函数，供 RLS 与函数使用 |
| `public.admin_audit_logs` | 操作留痕；管理员可读，只有 service_role 能写 |
| `public.admin_patient_stats()` | 按病人聚合记录数与首末日期，**仅 service_role 可执行**（`revoke ... from public/anon/authenticated`） |
| `revoke update on public.users` + `grant update (name)` | 用户只能改姓名，不能再篡改手机号 |

现有业务表策略**一行未改** —— 管理员的所有读写都经 service_role 完成，普通用户视角与改动前完全一致。

### 后端（`supabase/functions/admin-api/index.ts`）

单一入口，action 分发，共 20 个 action（`whoami` 之外都在 `HANDLERS` 路由表里）：

- 读：`whoami`、`stats.overview`、`user.list`、`user.get`、`patient.list`、`patient.get`、`audit.list`
- 写：`user.rename`、`user.setBanned`、`user.resetPassword`、`user.create`、`user.delete`、`admin.grant`、`admin.revoke`、`member.add`、`member.setRole`、`member.remove`、`patient.update`、`patient.transferOwner`、`patient.delete`

内置保护：不能禁用/删除/撤销自己、至少保留一名管理员、病人至少保留一名创建者、删除用户与病人需手输手机号/姓名确认、删除用户前检查其是否为某病人的唯一创建者。

### 前端（`src/admin/**`，Element Plus + hash 路由）

`admin/index.html` + `vite.admin.config.ts`（产物 `dist-admin/index.html`）＋ 8 个页面：登录、概览、用户列表、用户详情、病人列表、病人详情、操作日志、我的账号。含 30 分钟空闲自动登出、危险操作二次确认、重置密码结果一次性展示。

### 验证结果（2026-10-02，测试库 `gkrugenqmbimpzkkriml` 实测）

| 脚本 | 覆盖范围 | 结果 |
|---|---|---|
| `supabase/verify-admin-api.mjs` | 越权拦截与权限收口（A1～A6、B1～B3） | **10/10 通过** |
| `supabase/verify-admin-actions.mjs` | 全部 action 正向链路 + 保护逻辑 + 审计留痕 | **29/29 通过** |

关键证据：

- 普通用户调 `user.list` / `patient.delete` → **403 无后台权限**；不带 token → **401**
- 普通用户改自己 `phone` → **403（42501 权限不足）**；改 `name` → **200**（App 现有功能不受影响）
- 普通用户写 `public.admins` → **403**（无法自我提权）
- **管理员**直连 PostgREST 查 `sessions` → **空结果**（隐私边界在数据库层成立）
- 禁用账号后该账号**确实无法登录**，解禁后恢复
- 移除「唯一创建者」被拒绝；撤销自己的管理员权限被拒绝
- 审计日志覆盖全部 14 类写动作；临时数据跑完零残留
