> 配套文档：[后台管理系统设计说明.md](./后台管理系统设计说明.md)
> 适用：多人版（前端生产站 https://dialysis-49v.pages.dev ，后台 https://dialysis-admin.pages.dev ）

## 〇、组成与地址

| 部分 | 位置 | 部署方式 |
|---|---|---|
| 数据库增量 | `supabase/schema.sql` 第 9～13 节 | SQL Editor 执行（幂等，可重复跑） |
| 后台接口 | `supabase/functions/admin-api/` | `supabase functions deploy admin-api`（**保持 JWT 校验**） |
| 后台前端 | `admin/index.html` + `src/admin/**` | `npm run build:admin` → `dist-admin/index.html` → Pages 项目 `dialysis-admin` |
| 自动部署 | `.github/workflows/deploy-admin.yml` | push `main` 且改动命中后台相关路径时触发 |

App（`dist/` → Pages 项目 `dialysis`）与后台（`dist-admin/` → Pages 项目 `dialysis-admin`）**完全独立**，后台代码不会进 APK。

## 一、执行数据库增量（每个环境各一次）

1. Supabase Dashboard → 选择项目 → **SQL Editor** → New query
2. 粘贴 **整个** `supabase/schema.sql`（脚本幂等，重复执行只补缺的部分，不动数据）→ Run
3. 本次新增对象（第 9～13 节）：

| 对象 | 说明 |
|---|---|
| `public.admins` | 管理员名单 |
| `public.is_admin()` | 是否管理员（security definer） |
| `public.admin_audit_logs` | 后台操作日志 |
| `public.admin_patient_stats()` | 记录数聚合函数（仅 service_role 可执行） |
| `revoke update on public.users` / `grant update (name)` | 用户只能改姓名 |

> 建议先在**测试库**（ref `gkrugenqmbimpzkkriml`）跑通，再跑生产库（ref `vbamprkcwrpsazkyknjq`）。

## 二、部署后台接口

```bash
# register 需要 --no-verify-jwt；admin-api 恰恰相反，必须保留 JWT 校验
npx --yes supabase@latest functions deploy admin-api --project-ref <ref> --use-api
```

验证函数状态（`verify_jwt` 应为 true）：

```bash
curl -s -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" \
  "https://api.supabase.com/v1/projects/<ref>/functions" 
```

## 三、设置首个管理员

在 SQL Editor 执行一次（换成你自己的手机号）：

```sql
insert into public.admins(user_id, note)
select id, '初始管理员' from public.users where phone = '13800000000'
on conflict (user_id) do nothing;
```

确认：

```sql
select a.user_id, u.name, u.phone, a.created_at
from public.admins a join public.users u on u.id = a.user_id;
```

> 前提：该手机号必须已经在 App 里注册过（`public.users` 里有对应行）。
> 后台**不提供**自助提权入口，这是刻意的：只有数据库管理员能授予第一权限。

## 六、验收清单（逐条可复现）

### A. 越权拦截（最关键）

| # | 操作 | 预期 |
|---|---|---|
| A1 | 不带 token 调 `admin-api` | **401** `{"error":"未登录"}` |
| A2 | 普通用户 token 调 `user.list` | **403** `{"error":"无后台权限"}` |
| A3 | 普通用户 token 调 `patient.delete` | **403** |
| A4 | 普通用户 `insert into admins`（PostgREST） | 被拒（无写策略） |
| A5 | 普通用户 `update users set phone=...` | 被拒（列级权限，仅允许 `name`） |
| A6 | 普通用户查 `sessions` 明细 | 仍只看到自己是成员的病人（RLS 未变） |
| A7 | 管理员直连 PostgREST 查 `sessions` | **读不到别人的病历**（隐私边界在数据库层成立） |

A2/A3 可脚本化验证（把 `TOKEN` 换成普通用户的 access token）：

```bash
curl -s -o /dev/null -w "%{http_code}\n" -X POST \
  "https://<ref>.supabase.co/functions/v1/admin-api" \
  -H "Content-Type: application/json" \
  -H "apikey: <anon key>" -H "Authorization: Bearer <普通用户 token>" \
  -d '{"action":"user.list","payload":{}}'
# 期望输出 403
```

### A′. 正向功能（管理员能用）—— 一条命令跑完

```bash
node supabase/verify-admin-actions.mjs --env .env \
  --admin-phone <管理员手机号> --admin-password <密码> \
  --plain-phone <普通账号手机号> --plain-password <密码>
```

自动跑完全部 action：用 App 的 `create-patient` 建临时病人（顺带证明现有链路未被影响）→ 改病人配置 →
成员增删改角色 → 转移创建者（含「唯一创建者不可移除」保护）→ 改名 / 重置密码 / 禁用 / 解禁（并验证禁用后**真的登录不上**）
→ 授予 / 撤销管理员（含「不能撤销自己」）→ 代建账号 / 删除账号 → 删除病人 → 核对审计日志是否覆盖全部动作。

脚本只用临时数据或可逆操作，跑完不留残留（除审计日志）。测试库实测 **29/29 通过**。

## 七、常见问题

**Q：登录后台提示「无后台权限」**
该账号不在 `public.admins` 表里。用 §3 的 SQL 授予，或让已有管理员在「用户管理 → 用户详情 → 授予管理员」操作。

**Q：管理员在后台看不到某个病人**
后台的病人列表是**全量**的（service_role），看不到通常是筛选条件问题；若列表里也没有，说明该病人已被删除。

**Q：为什么后台看不到透析记录内容？**
这是设计选择（隐私边界）：后台只提供记录条数与首末日期。数据库层没有给管理员开放 `sessions` 等表的任何策略。

**Q：禁用了账号，为什么对方还能用一会儿？**
Supabase 签发的 access token 有效期内仍然可用（默认 1 小时），到期刷新时才会被拒绝。这是 GoTrue 的行为，不是 bug。

**Q：删除用户时提示「唯一创建者」**
该用户是某个病人的唯一 owner。先到病人详情页「设为创建者」转移给另一位成员，或改用「连同病人数据一并删除」。

**Q：CI 部署后台失败，提示项目不存在**
workflow 里已带 `wrangler pages project create ... || true`（幂等）。若 token 权限不足（需要 Account · Cloudflare Pages · Edit），到 Cloudflare 控制台手动建一个名为 `dialysis-admin` 的 Pages 项目即可。
