# 测试说明

> 目标：**每次改代码推送前，用几十秒把「改坏了」这件事挡在本机**；
> 即便漏过去了，CI 也会拦住部署 —— 测试不过，`deploy.yml` / `deploy-admin.yml` / `build-apk.yml` 都不会执行。

---

## 一、怎么跑

| 场景 | 命令 | 说明 |
|---|---|---|
| 跑一遍全部测试 | `npm test` | 最常用；约 20~40 秒 |
| 边写边跑（监听） | `npm run test:watch` | 改哪个文件跑哪个 |
| 带覆盖率 | `npm run test:coverage` | CI 用的就是这条；跌破阈值会红 |
| 只跑某层 | `npm run test:unit` / `npm run test:edge` | `unit` = 纯逻辑，`edge` = Edge Function |
| 只跑某个文件 | `npx vitest run tests/repo/localRepository.spec.ts` | 按路径过滤 |
| 只跑匹配名字的用例 | `npx vitest run -t '限流'` | 按用例名过滤 |
| 推送前全量检查 | `npm run verify` | 测试 + App 构建 + 后台构建 |

**关于 git 钩子**：`npm install` / `npm ci` 之后会自动安装（`package.json` 的 `prepare` 钩子调用
`scripts/install-hooks.mjs`）—— 因为 git 的钩子目录属于**本地配置**，不随仓库分发，每次装依赖都得重新注册一次。
需要手动重装时：

```powershell
npm run hooks:install
```

装完之后 `git push` 会自动先跑「类型检查 + 全部测试」，不通过就中止推送。
临时跳过：`SKIP_TESTS=1 git push`。

## 二、测试分层

```
tests/
├── setup/setup.ts          全局环境（fake-indexeddb、浏览器 API 兜底、env 断言）
├── helpers/                测试工具（造数据、假 Supabase、Edge 装载器）
│   ├── factories.ts        病人 / 干体重 / 透析记录 / 血压… 工厂
│   ├── fakeSupabase.ts     可编程 PostgREST 替身（不连真库）
│   ├── cloud.ts            云端模块替身（isCloudConfigured / client）
│   └── edge.ts             Edge Function 装载器（注入 Deno 全局）
├── unit/                   纯函数：计算、格式化、评估阈值、常量、id
├── repo/                   数据访问层：本地库、缓存、云端映射、迁移、分发
├── stores/                 登录态、当前病人
├── router/                 路由守卫（登录拦截、病人上下文）
├── lib/                    云端辅助（cloudAdmin）
├── views/                  App 页面组件（7 个页面 + App + BaseChart）
├── admin/                  后台管理端（lib/{api,auth,format} + views.spec.ts 覆盖 8 个页面）
├── edge/                   Edge Functions（register / create-patient / invite-member / admin-api / cors）
├── integration/            跨模块集成（真实 Dexie + 真实仓储，不 mock 数据层的端到端数据流）
└── guards/                 静态守卫（见下）
```

### 静态守卫（guards）是什么

把「编译器检查不到、但踩过坑的项目约定」写成可执行断言。它们不加功能，只是防止旧问题复发，例如：

- **敏感信息不得入库**：扫「已进索引 + 未跟踪但未被忽略」的全部文本文件（后者才最容易把密钥带进仓库），
  禁止出现 `sbp_` 开头的 PAT、JWT（`eyJhbGciOi`）、私钥块、真实 service_role key；
  并带**阳性对照**（合成假密钥必须被规则命中），防止规则被写废后「永远绿」
- **后台隐私边界**：`admin-api` 不得查询任何病历明细表（`sessions` / `blood_pressures` / …），只允许聚合 RPC；
  连 `selectAll` 的表白名单也一并锁死
- **管理员不可提权**：`schema.sql` 里 `admins` 表只允许 `for select` 策略，任何写策略（或省略 `for`＝ALL）都算提权后门
- **结构同步**：`cloudRepository` 写出的每个列名，必须都能在 `schema.sql` 里找到；`types.ts` 字段与行映射必须一一对应
- **三处仓储实现一致**：`Repository` 接口的方法在 local / cloud / cached 三个实现里都存在
- **云端读写的错误处理**（本轮事故固化）：读接口必须解构并检查 `error`（否则断网/401 会显示成「没有数据」，用户以为档案和记录丢了）、按 id 删除必须 `.select('id')` 复查影响行数（RLS 静默过滤 0 行时前端会以为删成功，几秒后记录「复活」）、缓存读函数必须带 `FRESH_MS` 闸门（否则与 `watch(cacheVersion)` 组成无限请求循环）、导入备份必须先整份校验再进事务清库（否则坏备份会先清空本机数据）
- **发布不变式**：`android/gradlew` 保持 100755、`cap sync` 生成的 gradle 文件必须被跟踪、APK 工作流里 `npm run build` 必须在 `cap sync` 之前

## 三、CI 是怎么接的

```
.github/workflows/
├── test.yml         ← 唯一的测试定义（on: workflow_call）：
│                        job 「测试与覆盖率」 + job「类型检查与构建」
├── ci.yml           ← 任何 push / PR 都调用 test.yml（尽早发现问题）
├── deploy.yml       ← test → deploy（needs: test）：测试不过不部署生产
├── deploy-admin.yml ← test → deploy：测试不过不部署后台
└── build-apk.yml    ← test → build：测试不过不出 APK
```

要点：

- 测试定义**只有一份**（`test.yml`），四处复用，不会出现「CI 跑的和我本地跑的不是一套」。
- 部署类工作流全部 `needs: test`，所以「测试失败 → 不部署」是硬保证，而不是发个通知。
- `test.yml` 里除了测试，还会跑 `npm run build`（含 `vue-tsc` 类型检查）、`npm run build:admin`、`npm run smoke:admin`，覆盖「测试过了但构建挂了」这类问题。

## 四、几条硬约定（写测试时容易踩）

1. **测试恒跑「纯本地单机模式」**
   `vitest.config.ts` 用 `envDir` 把 `.env` 的加载目录指走，`import.meta.env.VITE_SUPABASE_*` 永远为空。
   这样同一份用例在本机（`.env` 连测试库）和 CI（没有 `.env`）上结果完全一致。
   `tests/setup/setup.ts` 里有一条断言，一旦有人把 `.env` 带回测试会直接报错。

2. **要测云端分支，必须显式 mock**
   ```ts
   vi.mock('../../src/lib/supabase', () => fakeSupabaseModule({ configure: true, client }))
   ```
   `vi.mock` 会被提升到文件顶部，所以工厂必须自包含（不能引用外部变量）。

3. **不连真库、不发真请求**
   数据库用 `makeFakeSupabase()`，网络用 `vi.stubGlobal('fetch', ...)`。
   有测试联网 = 有测试会在别人机器上随机失败。

4. **Edge Function 也能直接测**
   `supabase/functions/**` 是 Deno 代码，但纯逻辑可以在 Node 下测：
   `tests/helpers/edge.ts` 会在 import 之前注入最小 `Deno` 运行时并把 `npm:@supabase/supabase-js@2` 换成替身。
   参考 `tests/edge/register.spec.ts`。

5. **覆盖率阈值在 `vitest.config.ts`**
   当前阈值见文件里的 `coverage.thresholds`。阈值只允许**上调**；要下调必须在提交信息里写清原因。

## 五、新增测试怎么写

**纯函数 / 常量**（最简单，放 `tests/unit/`）：

```ts
import { describe, it, expect } from 'vitest'
import { 要测的函数 } from '../../src/utils/xxx'

describe('xxx · 分组名', () => {
  it('中文描述：什么输入 → 什么结果', () => {
    expect(要测的函数(输入)).toBe(期望)
  })
})
```

**需要云端分支**（`src/lib/**`、`src/repo/**`、`src/stores/**`）：

```ts
import { vi } from 'vitest'
import { makeFakeSupabase } from '../helpers/fakeSupabase'

const fake = makeFakeSupabase({ tables: { patients: [{ id: 'p1' }] } })

// 工厂必须内联（vi.mock 会被提升到文件顶部）
vi.mock('../../src/lib/supabase', () => ({
  isCloudConfigured: true,
  supabase: fake.client,
  SUPABASE_URL: 'https://test-project.supabase.co',
  SUPABASE_ANON_KEY: 'test-anon-key',
}))
```

**Edge Function**（`supabase/functions/**`，文件首行加 `// @vitest-environment node`）：

```ts
import { loadEdgeFunction, edgeRequest, readResult } from '../helpers/edge'

const h = await loadEdgeFunction(() => import('../../supabase/functions/xxx/index.ts'), {
  env: { TURNSTILE_SECRET_KEY: 'secret' },
  fakeOptions: { rpc: { check_rate_limit: () => true } },
})
const { status, body } = await readResult(await h.handle(edgeRequest({ ... })))
```

**静态守卫**（放 `tests/guards/`）：用 `node:fs` / `git ls-files` 读源码与索引做断言——
适合固化「改了 A 就必须同时改 B」这类约定。

自检清单（提交前）：

- [ ] 新增/改动的分支都有用例（尤其是错误分支与边界值）
- [ ] 没有真实网络请求、没有对当前时间的隐式依赖（用 `vi.setSystemTime` 固定）
- [ ] 名字说人话：失败时看名字就知道坏在哪
- [ ] `npx vitest run <文件>` 单独跑能过，`npm test` 全量也能过

## 六、已知缺陷的断言约定

写测试时如果发现产品行为有问题（但本次任务不该改产品代码），按这个约定处理：

1. **断言「当前实际行为」**，不要写期望值 —— 否则 CI 会一直红，等于用测试锁死了修复路径。
2. 用例名 + 注释里标明 `⚠️ 已知缺陷：`，写清「现象 / 期望 / 影响」。
3. 修复该缺陷时，**同步把断言改成期望值**（用例名去掉「已知缺陷」）。

这样缺陷不会被遗忘，也不会阻挡修复。检索全部已知缺陷：

```powershell
Select-String -Path tests\*\*.spec.ts -Pattern '已知缺陷' | Select-Object Path,LineNumber,Line
```

## 七、没覆盖到的部分（诚实清单）

- **真实浏览器行为**：jsdom 没有布局引擎，Vant 弹窗/滚动的视觉效果测不到 —— 仍需 `npm run dev` 人工看一眼。
- **真实 Supabase 链路**：RLS 越权、跨账号可见性靠真库验证（`docs/后台管理系统部署指南.md` 第六节、`supabase/verify-*.mjs`）。
  单测里的假客户端**不校验 RLS**，所以守卫测试用源码文本断言兜住「后台不得碰病历表」这条底线。
- **APK 产物**：签名、`debuggable`、连的哪个库，只有 CI 出包后校验（`build-apk.yml` 里那几段）。
- **ECharts 实际渲染**：测试里 mock 掉，只验数据与调用，不验图形。
